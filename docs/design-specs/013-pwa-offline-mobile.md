# SPEC-013: PWA, offline reading, and mobile polish

- **Status:** Todo
- **Phase:** 3
- **Depends on:** SPEC-004 (reading pane), SPEC-005 (read/star state)
- **Estimated size:** L

## Context

`apps/web` is a plain Vite + React 19 SPA. `vite.config.ts` has only
`react()` and `tailwindcss()` plugins and no service worker. `index.html`
already sets `viewport-fit=cover` and `color-scheme: light dark`, but there
is no web app manifest, no installability, and nothing works offline: a
reload with no network shows the browser error page. `queryClient.ts` builds
a bare `QueryClient` with an in-memory cache that is discarded on reload, so
even already-fetched lists and article bodies vanish offline. Read/star
mutations (SPEC-005) fire straight through and fail hard with no connection.

SPEC-004 gives us the reading pane and a responsive layout that drops the
third column below `lg`; SPEC-005 gives us the optimistic read/star and
mark-read mutations. This spec makes the app installable, keeps previously
fetched content readable offline, queues state changes for replay, and
refines the sub-`lg` layout into a real phone navigation flow.

## Goal

The user can install Reader to their home screen and launch it standalone.
Offline, the app shell loads instantly and any list they have already
scrolled and any article they have already opened stay readable. Read/star
taps made offline are queued and replay automatically on reconnect. On a
phone the three panes become a stacked feeds -> list -> reader flow with
back navigation, a swipe between list and reader, and comfortable touch
targets under the notch and home indicator.

## Non-goals

- Background sync of new feed content while the app is closed (push, periodic
  background fetch). Offline is limited to what was fetched while open.
- Offline full-text search (SPEC-006) or offline OPML (SPEC-009).
- Caching the Web view iframe or Simplified extraction of un-opened articles
  (SPEC-004); only opened article detail responses are cached.
- Persisting per-user settings offline beyond what the query cache holds
  (SPEC-011 owns settings).

## Data model changes

None.

## API changes

None required. Note for the API owner: `GET` list and detail routes should be
cache-friendly where safe so the service worker's runtime cache can
revalidate cheaply. Add `ETag` + `Cache-Control: private, max-age=0,
must-revalidate` to `GET /api/articles`, `GET /api/articles/:id`,
`GET /api/feeds`, and `GET /api/counts` so a stale-while-revalidate fetch can
304 instead of re-sending the body. Never cache-header the auth or mutation
routes. This is an optimization, not a correctness dependency for this spec.

## Web / UI changes

### PWA shell (`vite-plugin-pwa`)

- Add `vite-plugin-pwa` (dev dep) and register it in `vite.config.ts` with
  `registerType: 'prompt'` (we drive our own update prompt) and
  `strategies: 'generateSW'` (Workbox).
- Web app manifest (generated by the plugin):
  - `name: 'Reader'`, `short_name: 'Reader'`, `display: 'standalone'`,
    `start_url: '/'`, `scope: '/'`, `orientation: 'portrait-primary'`.
  - `theme_color` and `background_color` set to a static hex approximation of
    the light `--background` token (`#ffffff`); the manifest cannot read the
    oklch CSS variables, so hard-code and add a comment linking to
    `index.css`. Provide a dark-matching `theme_color` via a
    `<meta name="theme-color" media="(prefers-color-scheme: dark)">` in
    `index.html` mapped to `--background` dark (`#12151c`), light meta to
    `#ffffff`.
  - Icons: `192x192`, `512x512`, plus a `512x512` `purpose: 'maskable'` icon
    with the primary-token accent and safe-zone padding. Store sources under
    `apps/web/public/icons/`.
- Workbox service worker:
  - `precache` the built app shell (JS/CSS/HTML/fonts) via the plugin's
    injected manifest, with `navigateFallback: '/index.html'` so any route
    loads offline; exclude `/api/` from the navigation fallback.
  - Runtime-cache `GET /api/**` with `StaleWhileRevalidate`, a dedicated
    cache name (`api-cache`), an `ExpirationPlugin` (maxEntries ~200, maxAge
    ~7 days), and `cacheableResponse` for status `0` and `200`. Do not
    runtime-cache non-GET requests.
  - `skipWaiting: false`, `clientsClaim: false`; the update prompt controls
    activation.

### Install and update affordances

- `apps/web/src/lib/pwa.ts`: a small hook layer.
  - `useInstallPrompt()`: captures the `beforeinstallprompt` event, exposes
    `canInstall` and `promptInstall()`. Render an "Install Reader" item in the
    app menu / settings, hidden when `canInstall` is false or the app is
    already in `display-mode: standalone`.
  - `useServiceWorkerUpdate()`: wraps the plugin's `registerSW({ onNeedRefresh,
    onOfflineReady })`. On `onNeedRefresh`, show a non-blocking toast
    ("A new version is available - Reload") whose action calls
    `updateSW(true)`. On `onOfflineReady`, show a one-time "Ready to work
    offline" toast.
- Register the SW from `main.tsx` (via the plugin's virtual
  `virtual:pwa-register/react` module), inside the existing providers.

### Offline query persistence

- Add `@tanstack/query-async-storage-persister`, `@tanstack/react-query-persist-client`,
  and `idb-keyval` (IndexedDB is required; localStorage is too small for
  article bodies). Wrap the app in `PersistQueryClientProvider` in `main.tsx`,
  replacing the plain `QueryClientProvider`.
- Persister: `createAsyncStoragePersister({ storage: { getItem, setItem,
  removeItem } })` backed by `idb-keyval`, `key: 'reader-query-cache'`,
  `throttleTime: 1000`.
- In `queryClient.ts`, raise `gcTime` to at least 24h so cached lists and
  article bodies survive long enough to be persisted and rehydrated; keep
  `staleTime: 30_000` so online views still revalidate.
- `persistOptions`: a `buster` string tied to the app build id (bump to drop
  stale caches on breaking shape changes), `maxAge: 7 days`, and a
  `dehydrateOptions.shouldDehydrateQuery` that persists only `['articles', ...]`,
  `['article', id]`, `['feeds']`, and `['counts']` queries - never auth
  (`['session']`) or search results.
- Result: lists the user has scrolled and articles they have opened render
  from the persisted cache on an offline launch; the reading pane shows cached
  `contentHtml`/`readableHtml`. The Web-view iframe and un-opened articles are
  explicitly unavailable offline - show an inline "Not available offline" note
  in those cases rather than a spinner that never resolves.

### Offline mutation queue (read/star replay)

- Give SPEC-005's mutations stable `mutationKey`s (`['toggle-state']`,
  `['mark-read']`) and register default mutation functions on the client via
  `queryClient.setMutationDefaults(key, { mutationFn, onMutate, ... })` so a
  rehydrated paused mutation knows how to run.
- Persist the mutation cache alongside the query cache (the persist client
  handles this) so mutations made offline survive a reload.
- On startup after rehydration, call `queryClient.resumePausedMutations()`;
  also resume on the `online` event (`window.addEventListener('online', ...)`).
  TanStack Query pauses mutations automatically when `navigator.onLine` is
  false, so an offline read/star is optimistic locally, queued, and replayed
  in order on reconnect.
- Keep `onMutate` optimistic updates (SPEC-005) so offline taps reflect
  immediately in the cache and the persisted badges; `onSettled` invalidation
  simply no-ops until connectivity returns.
- Show a subtle "offline - changes will sync" indicator driven by an
  `useOnlineStatus()` hook so the queued state is visible, cleared once
  `resumePausedMutations()` settles.

### Mobile navigation

- Refine SPEC-004's sub-`lg` layout in `ReaderPage.tsx` into a three-step
  stacked flow on phones: feeds (sidebar) -> article list -> reader. Track a
  `mobileView: 'feeds' | 'list' | 'reader'` derived from the existing
  selection state (a selected feed advances to `list`, a selected article to
  `reader`); at `lg` and up the persistent three-column grid is unchanged.
- Back navigation: a top-bar back control at each step (reader -> list ->
  feeds) that pops one level without losing list scroll position or filters
  (reuse SPEC-004's back control, extend it up the stack). Wire the hardware /
  browser back button to the same pops via history state so Android back and
  the swipe-back gesture behave.
- Swipe gesture between list and reader: a lightweight pointer/touch handler
  (or `framer-motion` drag if already present) - swipe right in the reader
  returns to the list, swipe left on a list row's open affordance advances;
  keep it a progressive enhancement over the tap targets, never the only way.
- Nav bar: a bottom nav on phones (All / Starred / Search / Settings) fixed
  above the home indicator; a compact top bar carries the contextual back
  control and title. Above `md` the existing sidebar nav is authoritative and
  the bottom bar is hidden.
- Safe-area insets: apply `env(safe-area-inset-*)` padding to the top bar,
  bottom nav, and scroll containers (Tailwind arbitrary values, e.g.
  `pb-[env(safe-area-inset-bottom)]`); `viewport-fit=cover` is already set.
- Touch targets: bump interactive rows and icon buttons to a >=44px hit area
  on `< md` (list rows, star/read toggles, view switcher, nav items).

## Implementation notes

- Build order: manifest + icons + plugin wiring (verify installability first),
  then Workbox runtime caching, then query persistence, then the offline
  mutation queue, then mobile nav and gestures last.
- The service worker only runs on the built app (`pnpm build` +
  `vite preview`) and over HTTPS/localhost; `pnpm dev` uses
  `devOptions.enabled` sparingly - test offline against a preview build, not
  the dev server.
- Gotcha: `PersistQueryClientProvider` must gate rendering on rehydration
  (`onSuccess`) so mutations don't resume before defaults are registered.
- Gotcha: bump the persist `buster` whenever a persisted query's response
  shape changes (e.g. SPEC-004/005 payload edits) to avoid rendering stale
  shapes.
- Security: the SW must never cache authenticated responses in a way that
  leaks across users on a shared device - the query cache is keyed per app
  install, and on logout call `queryClient.clear()` plus purge the idb-keyval
  key and the Workbox `api-cache`. Do not runtime-cache `Set-Cookie` or auth
  routes.
- Keep changes inside `apps/web`; no API or schema work is required to ship.

## Acceptance criteria

- [ ] The app is installable: a valid manifest, registered service worker,
      and icons; Chrome shows the install prompt and it launches standalone.
- [ ] Offline (DevTools offline, or airplane mode on device), a cold reload
      shows the app shell, not the browser error page.
- [ ] An article list the user scrolled while online renders offline from the
      persisted cache; an article opened while online is readable offline
      (Readable/Simplified body shown, Web view shows "Not available offline").
- [ ] An article never fetched while online shows a clear "Not available
      offline" state, not an infinite spinner.
- [ ] Toggling read/star offline updates the UI and badges immediately, and
      the changes replay to the server automatically on reconnect (verified
      against `article_states`), in order, exactly once.
- [ ] An "offline / changes will sync" indicator appears offline and clears
      after reconnect sync completes.
- [ ] An "update available" prompt appears when a new build is deployed and
      reloading activates the new service worker.
- [ ] On a phone width, navigation is a stacked feeds -> list -> reader flow;
      back controls and the browser/hardware back button pop one level without
      losing list scroll position or filters; a swipe moves between list and
      reader.
- [ ] Bottom nav and top bar respect safe-area insets under the notch and home
      indicator; interactive targets are >=44px on phone widths.
- [ ] Lighthouse PWA / installability audits pass (installable, SW registered,
      offline-capable, correct theme/viewport).

## Testing

- Unit: `useOnlineStatus` and the persister storage adapter (get/set/remove
  round-trip against a mocked idb-keyval).
- Unit: `dehydrateOptions.shouldDehydrateQuery` persists only the whitelisted
  query keys and excludes `['session']` and search.
- Integration (web): with `navigator.onLine` mocked false, a read toggle is
  optimistic and paused; flipping online and firing `resumePausedMutations()`
  issues the PATCH exactly once and settles the cache.
- Integration (web): rehydrating a persisted cache renders a cached list and
  article-detail offline without a network call.
- Manual: install to home screen on iOS Safari and Android Chrome, launch
  standalone, confirm theme color and safe-area layout.
- Manual: online, open several articles and scroll a list; go offline, reload,
  confirm those are readable and an un-opened article is not.
- Manual: offline, star and mark-read several items, reconnect, confirm the
  server state matches and badges reconcile.
- Manual: deploy a new build, confirm the update prompt and that reloading
  serves the new assets.
- Automated: run Lighthouse (CI or `lighthouse` CLI) against a preview build
  and assert the PWA/installability checks pass.

## Open questions

- iOS Safari ignores `beforeinstallprompt`; do we show an "Add to Home Screen"
  hint with instructions on iOS instead of the install button, or leave install
  to the browser share sheet?
- Do we cap the persisted `api-cache` / query cache size on low-storage
  devices, or rely on `ExpirationPlugin` and `maxAge` eviction alone?
